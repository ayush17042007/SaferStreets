# PART B: PRODUCTION-GRADE BACKEND ADDENDUM

"Production-grade" here means correct under concurrency, safe by default, observable, recoverable and deployable by a small team. The Appendix defines **what** to build; this part defines **how well**.

## B1. Architecture
- **Modular monolith** (Appendix 7.1) with **two entrypoints** from `apps/api`: `server.ts` (HTTP) and `worker.ts` (pg-boss jobs). Both run from one Docker image; start with `ROLE=server` and `ROLE=worker` as two processes or services (or one container running both at first).
- Layers: routes, controller, service (business rules, transactions), repository (Prisma). No business logic in controllers. Shared Zod schemas in `packages/shared` are used by web and API.
- Config via a single validated env module (zod); the app **fails fast** on invalid config.
- Graceful shutdown (stop accepting requests, finish in-flight work, close pg-boss and Prisma). Request timeouts. Body size limits.

## B2. Same-origin API and cookies
Serve the web app and API on **one origin**: Next.js `rewrites` proxy `/api/*` to the Express service. Session cookie: `httpOnly`, `Secure`, `SameSite=Lax`, `Path=/`. This removes CORS complexity and most CSRF exposure. Keep the custom-header CSRF check (`X-Requested-With`) on state-changing requests and an `Origin` check. SSR data fetching forwards the cookie.

## B3. Jobs and safety-critical scheduling (pg-boss)
Replace node-cron and the in-process email queue. All jobs are **idempotent**, retry with exponential backoff, and have dead-letter handling.

| Job | Schedule | Notes |
|---|---|---|
| `journey.scan` | every minute | Moves ACTIVE to OVERDUE at ETA + 10 min; emails the user; at ETA + escalation (default 30 min) emails the trusted contact once (guard with `contact_notified_at` inside a transaction using `SELECT ... FOR UPDATE SKIP LOCKED`) |
| `email.send` | on demand | One job per email, retries (5 attempts), writes `email_events`, never blocks request paths |
| `ride.lifecycle` | every 5 min | Auto in-progress and completed, expire pending requests |
| `alert.expire` | every 10 min | 6 h expiry; set EXPIRED |
| `alert.fanout` | on demand | Radius and category matching in batches of 200; one notification and email job per recipient |
| `cleanup.nightly` | 02:00 IST | OTP, sessions, notifications, orphan uploads, retention rules (Appendix 6.5), journey data purge |
| `scheduler.heartbeat` | every minute | Writes a heartbeat row; **an external uptime check alarms if the heartbeat is older than 3 minutes** (journey reminders are safety-relevant) |

**Safety-critical email rule:** if an overdue or contact email fails after retries, mark it failed, alert the team (Sentry plus log), and show the user in-app a clear fallback ("We couldn't email Mom. Call them directly.").

## B4. Data model additions (on top of Appendix 6)
- `idempotency_keys` (`key`, `user_id`, `method`, `path`, `request_hash`, `response_status`, `response_body`, `created_at`, `expires_at`; unique on `(user_id, key)`).
- `user_blocks` (`blocker_id`, `blocked_id`, `created_at`; PK both) used by ride requests and chat.
- `uploads` (`id`, `user_id`, `purpose`, `storage_key`, `status` PENDING/ATTACHED/ORPHANED, `created_at`) for orphan cleanup.
- `email_events` (`id`, `notification_id`, `to_hash`, `template`, `provider_id`, `status` QUEUED/SENT/DELIVERED/BOUNCED/COMPLAINED/FAILED, `error`, `created_at`) plus an `email_suppressions` list fed by provider webhooks.
- `heartbeats` (`name`, `last_seen_at`).
- `consents` (`user_id`, `type` TERMS/PRIVACY/ALERT_OPTIN, `version`, `accepted_at`, `ip_hash`).
- `ride_waitlist` [OPT].
- Add `version` (int) columns for optimistic concurrency on `rides` and `reports` where edited concurrently.
- Every table has `created_at`/`updated_at`; every foreign key is indexed; soft delete only where Appendix 6 says so.

## B5. API conventions (additions)
- **Idempotency-Key** header supported on `POST /rides`, `/reports`, `/alerts`, `/journeys` and the ride accept endpoint; the same key and body returns the original response.
- **Cursor pagination** for reports, rides, alerts and notifications: `?cursor=...&limit=20` returns `{ data, meta:{ nextCursor } }`. Admin tables may use offset.
- **OpenAPI 3.1** generated from the Zod schemas; served at `/api/docs` in non-production and to admins in production. A contract test fails CI if the spec and routes drift.
- **Health:** `GET /health/live` (process up) and `GET /health/ready` (DB reachable, migrations applied, worker heartbeat fresh). Never expose secrets or versions to the public.
- Consistent error model (Appendix 7.2) with a `requestId` field. Validation errors list field paths. No stack traces in responses.
- Rate limiting via the shared Postgres store; limits keyed by user ID when authenticated, otherwise IP. Return `Retry-After`.
- Geo search: bounding-box prefilter plus Haversine; add a composite index on lat/lng and consider `earthdistance` later; **PostGIS stays [FUTURE]**.

## B6. Observability
- **pino** JSON logs with `requestId`, `userId` (hashed where needed), route, latency, status. Redact emails, phones, tokens and OTPs.
- **Sentry** for web and API (release tags, source maps). Alert on error-rate spikes, job failures, and failed safety-critical emails.
- Metrics (counts and latencies for key flows: OTP requests, report submits, accepts, journey overdue emails, alert fan-outs) exposed at an internal `/metrics` or via logs.
- Uptime monitoring on `/health/ready` and the scheduler heartbeat.
- Audit log (`moderation_actions`) is append-only; admin actions always carry a reason.

## B7. Security additions (on top of Appendix 9)
- **Cloudflare Turnstile** (or equivalent) on the OTP request form to stop email bombing; keep per-email and per-IP limits.
- Strict **CSP** with nonces, HSTS, `helmet`, `Referrer-Policy`, `Permissions-Policy` (geolocation only on user action), cookie flags as in B2.
- Session rotation on login, concurrent-session list, revoke-all, suspended/banned users rejected on every request.
- Authorization is **deny by default**, enforced in services; an automated **IDOR test suite** hits every `:id` route as a different user.
- Uploads: signed direct upload, MIME allow-list, 5 MB cap, EXIF stripped, re-encoded to WebP, random keys, per-user quota, orphan cleanup.
- Dependency scanning (Dependabot, `npm audit` in CI), secret scanning, lockfile enforcement, minimal Docker image running as a non-root user.
- Abuse prevention for SafeAlert and rides exactly as in Appendix 2B/2D and 9.
- Never log or return other users' emails or phone numbers.

## B8. Email
Resend with a **verified sending domain** (SPF, DKIM, DMARC). Branded HTML plus plain-text templates for OTP, journey start notice, overdue reminders, contact escalation, all-clear, ride request/decision, report status, alert notice (always including the "Unverified" label and the 112 disclaimer). Handle bounce and complaint webhooks (signature verified) by suppressing addresses. Every email to a trusted contact includes a one-click opt-out.

## B9. Uploads and maps
- Cloudinary (or S3-compatible storage) with signed uploads; the API stores only keys and URLs after server-side validation.
- MapTiler key restricted by allowed origins; MapLibre style JSON versioned in the repo; geocoding calls proxied through the API with caching and rate limits to protect the key.

## B10. Environments, CI/CD and operations
- Environments: local, staging, production, each with its own database and secrets. `.env.example` documents every variable.
- **GitHub Actions:** install, lint, typecheck, unit tests, integration tests (Postgres service container), build, Playwright E2E, a11y checks, dependency audit. Preview deployments for the web app.
- Migrations: `prisma migrate deploy` as a release step; **expand/contract** for risky changes; never edit applied migrations.
- Hosting suggestion: Vercel (web), an always-on host such as Render, Railway or Fly.io (API and worker, **must not sleep**), Neon or Supabase Postgres with **point-in-time recovery and tested restores**, Cloudinary, Resend, Sentry.
- Backups verified quarterly; runbook covering incidents (email provider outage, DB failover, worker stuck, spam wave) and moderator onboarding; first-admin bootstrap script.

## B11. Performance targets
- API p95 under 300 ms for list endpoints with 10k seeded reports, rides and alerts; p95 under 150 ms for simple reads.
- Web: LCP under 2.5 s on mid-range mobile over 4G; Lighthouse >= 90 on landing.
- Accept-ride endpoint is correct under 50 parallel requests for the same seat (never oversells).
- k6 smoke and load scripts committed to the repo.

## B12. Quality gates
- Unit, API, integration, E2E, a11y, visual-regression and permission-matrix suites (Appendix 11) must pass in CI.
- Coverage thresholds: services and utilities at least 80%; permission and IDOR suites cover every route.
- Test the safety-critical jobs with a controlled clock: overdue at +10, contact email at +30 (or the user's setting), idempotency on retry, extension just before overdue, completion during escalation.
